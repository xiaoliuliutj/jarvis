# Jarvis 企业级 Agent 平台：目标与演进路线

> 状态：长期设计基线（2026-11-25）
> 当前阶段：**不重构 Jarvis 内核，先把 App 管理系统做出来**。
> 用途：作为后续迭代、代码预留和架构决策的记录；不是一次性实施计划。

---

## 1. 目标

把现在的个人 Jarvis，逐步演进成一个「企业级 Agent 平台」：

- 每个用户有一个**边缘内核（Edge Kernel）**，运行在用户自己的主机上，负责操作本机、执行工具。
- 一个**管理系统**（手机 App / PC Web）负责交互、配置、用量、任务和审批。
- 一套**数据与控制面**集中管理用户数据（对话历史、用户数据、任务等）和工具注册表。
- 工具体系**共享**，不按用户复制；工具执行在各自内核，权限/配置按用户。

最终形态：**Jarvis 负责执行，管理系统负责治理，数据面负责沉淀**。

---

## 2. 设计原则

1. **稳定优先**：内核先不动，先加边界，后拆服务；不做大爆炸式重写。
2. **凭证不离开内核**：模型凭证、设备密钥只存在用户自己的内核；数据面只存「已配置/未配置」状态。
3. **工具三层分离**：
   - 工具注册表（共享元数据/版本/权限）
   - 工具运行时（每个内核执行；本地工具只能在本机）
   - 用户配置（启用/参数/配额，按用户）
4. **API first**：所有跨进程交互走版本化 API（`/api/v1`）；`tenant_id` 从第一天预留，但先单租户。
5. **可观测、可审计、可回滚、可计费**：每个工具调用、模型输出、审批都留痕。
6. **不破坏现有体验**：微信、PC、现有 App 通道继续可用；新结构逐步替换，不一次性切换。
7. **高风险动作必须有人类审批或确定性校验**：模型是概率性的，不能让它无约束地操作生产。

## 3. 目标架构

```text
┌─────────────────────────────┐
│  管理系统（手机 App / PC）    │
│  聊天 / 历史 / 用量 / 配置    │
│  任务卡 / 审批 / 通知         │
└──────────────┬──────────────┘
               │ HTTPS / WS（租户 token）
┌──────────────▼──────────────┐
│  数据与控制面（Data Plane）   │
│  租户/身份/会话/用量/任务     │
│  工具注册表/策略/审计/中继    │
│  不存明文凭证，不执行工具     │
└──────────────┬──────────────┘
               │ 出站 WS / HTTPS
┌──────────────▼──────────────┐
│  边缘内核（每个用户一份）      │
│  Agent 循环 / 模型调用        │
│  工具执行 / 本地文件 / 缓存   │
│  本机凭证 / 离线队列          │
└──────────────┬──────────────┘
               │
        微信 / 本机桌面 / 本地工具
```

### 3.1 边缘内核（现有 Jarvis）

- Agent 循环、模型调用、工具执行、记忆、会话、cron。
- 本机工具（截图、键鼠、本机文件）只能在这里执行。
- 凭证只在这里；数据面只拿非敏感元数据。
- 尽量无状态：上下文从数据面取，结果写回；本地缓存 + 离线队列。
- 主动出站连接数据面，避免要求用户开公网端口。

### 3.2 数据与控制面

- 租户、用户、设备、角色、权限。
- 会话历史、消息、任务卡、用量、审批、审计。
- 工具注册表：名称、描述、schema、版本、签名、权限、归属。
- 策略引擎：谁能对什么数据做什么；高风险动作审批。
- 中继：管理系统 ↔ 内核的消息路由（内核出站连接）。
- 不保存明文凭证；不直接执行工具代码。

### 3.3 管理系统

- 聊天、历史、文件、图片、提醒。
- 用量/费用/预算面板。
- 配置管理（非敏感）；敏感配置只显示状态。
- 任务卡、进度、审批、暂停/恢复。
- 只做客户端和薄 BFF，不复制内核业务逻辑。

## 4. 企业级能力清单（八根支柱）

### 4.1 身份、租户与权限
- 多租户隔离：tenant_id 贯穿数据/工具/模型/计费。
- SSO（OIDC/SAML）、SCIM、组织/角色；RBAC + ABAC。
- 设备注册、配对码、mTLS、远程注销/擦除。
- 服务间短期 token、密钥轮换、最小权限。

### 4.2 数据安全与合规
- TLS、存储加密、KMS/HSM、字段级加密/脱敏。
- 数据分级分类、PII、保留期限、导出/删除权。
- 数据驻留、备份加密、恢复演练、DLP。
- 供应链安全：依赖扫描、SBOM、镜像/工具包签名。

### 4.3 Agent 安全与治理
- Prompt 注入/越狱防护；工具结果视为不可信输入。
- 工具白名单、参数校验、沙箱、网络出口控制、凭证注入。
- 高风险动作人工审批（双人复核）；策略引擎（OPA/Cedar）。
- 预算/配额/步数/时间上限；循环检测、熔断、全局 kill switch。
- 内容安全、结构化输出、低置信度转人工。

### 4.4 运行时与编排
- 长任务状态机：持久化、断点续跑、暂停/恢复、审批门。
- 按租户隔离队列、优先级、背压；资源隔离。
- 幂等、重试、死信队列、补偿。
- Agent/Prompt/工具/模型版本化；灰度/回滚。
- 边缘内核：自动更新、健康检查、离线缓存、远程配置、NAT 穿透。

### 4.5 模型与工具平台
- 模型网关：多供应商抽象、故障转移、限流、超时、缓存、成本路由。
- 数据条款：不训练、不留存、区域合规。
- Prompt/知识库版本管理、评测集、回归、灰度。
- 工具注册表 + 签名 + 权限 + 配额；共享目录、按租户启用。
- 本地工具在边缘执行，云端工具在沙箱执行，统一审计。
- RAG 治理：知识库权限、文档版本、引用溯源、过期清理。

### 4.6 可观测与评测
- OpenTelemetry：用户 → Agent → 模型 → 工具全链路 trace。
- Agent 指标：任务成功率、工具成功率、平均步数、token/费用、延迟、人工介入率。
- 成本归因；离线评测、回归、LLM-as-judge、人工抽检、A/B、红队。
- 告警/SLO、值班、回放。

### 4.7 可靠性与运维
- 高可用、多副本/多可用区、无状态化、健康检查、故障转移。
- 容灾 RPO/RTO、跨区备份、切换演练。
- 容量规划；CI/CD、IaC、环境隔离、回滚。
- 降级：模型/工具不可用时兜底；离线模式。
- 安全运营：漏洞管理、渗透、红队、应急、SIEM/SOC。

### 4.8 商业化与运营
- 计量计费：token/任务/席位；配额、超额、发票、成本分摊。
- 租户生命周期：开通/试用/升级/停用/导出/删除。
- 管理控制台：租户、用量、审计、策略、工单。
- SLA、状态页、文档、培训、runbook。
- 合规认证：等保、ISO 27001、SOC 2（按目标市场）。

## 5. 当前 Jarvis 映射与差距

### 5.1 已有的

- `core/`：paths、config、principals、user-store、prompt、permissions、tools、conversation、scheduler、cron、schedule-store、logger、files、sticker-library、file-parsers、file-writers、image-providers。
- `bridge/server.mjs`：HTTP + WS、adapter、每用户调度、cron、日程、App adapter。
- `agents/agent.mjs` + `agents/tools/`：Agent 循环和系统工具。
- `userdata/<principalId>/`：persona、sessions、memory、workspace、crons、schedules。
- 已有 App 通道（`bridge/adapters/app.mjs`）、PWA、安卓 WebView 壳。

### 5.2 差距

- 没有 `tenant_id`、没有统一 `/api/v1`、没有管理系统专用 API。
- 用量只有 turn cost/turns，没有完整 token/成本/预算体系。
- 工具注册表是简单 JSON，没有版本/签名/租户权限。
- 没有任务卡/长任务 runner/审批流/策略引擎。
- 没有独立数据面；会话/记忆在本地文件。
- App 目前是聊天客户端，还不是管理系统。

### 5.3 暂时不动

- 现有 Agent 循环、工具实现、微信 adapter、cron/日程、文件解析/生成，先保持稳定。
- 只在新功能里预留接口和字段，不重构现有模块。

## 6. 路线图

### Phase 0（现在，1～2 周）：App 管理系统 MVP
- 保持内核不动；App 作为管理系统客户端。
- 功能：聊天、历史、文件/图片、提醒、用量只读、非敏感配置只读。
- 复用现有 App adapter；不引入数据面。
- 验收：手机可用、不暴露凭证、不影响微信/PC。

### Phase 1（2～4 周）：API 边界与管理能力
- 在现有 Bridge 上增加 `/api/v1` 门面（会话、消息、用量、配置状态）。
- 用量存储：每轮 input/output token、费用、工具调用；用量面板。
- 非敏感配置管理（persona、cron、日程、adapter 开关）；敏感配置只显示状态。
- 预留 tenant_id（默认 `personal`）。
- App：历史、用量、设置页面。

### Phase 2（1～2 个月）：内核模块化
- 抽出 user-store/memory/sessions/tools/usage 的 Repository/Service 接口。
- 工具注册表元数据（版本/权限/签名），工具代码仍在受控目录。
- 任务卡 + 长任务 runner MVP（状态、检查点、暂停、审批门）。
- 高风险动作策略/审批；审计日志。

### Phase 3（3～6 个月）：多租户控制面
- 独立数据服务（会话、用户数据、任务、用量）；租户隔离、SSO、设备配对、中继。
- 工具注册表服务 + 签名产物 + 沙箱运行时。
- 可观测（OTel）、预算、配额、计费。

### Phase 4（6～12 个月）：企业级
- 高可用/容灾、合规（等保/ISO/SOC 2）、SSO/SCIM、计费、支持、管理控制台、评测/红队、数据驻留。

## 7. 现在就要预留的扩展点（不实现）

- `tenantId`：principals/config 预留字段，默认 `personal`。
- `core/usage.mjs`：统一用量接口；每轮记录 token/费用/工具调用。
- `core/task-store.mjs`：任务卡接口；为长任务 runner 预留。
- `core/tool-registry.mjs`：工具元数据与工具代码分离；预留版本/权限/签名。
- `/api/v1`：新接口统一前缀；旧接口保留兼容。
- `core/data-access/`：user-store/memory/sessions 的访问接口；以后可替换为 HTTP。
- 配置分级：敏感 vs 非敏感；敏感只读状态，不经过模型。
- Adapter 接口：渠道与内核解耦；App 作为客户端。
- 事件总线/WS 事件：为管理系统实时推送预留。

> 这些只是「留位置」，不改变现有行为；等真正做对应阶段时再实现。

## 8. 近期行动（App 优先）

1. 先完成 App 管理系统 MVP：聊天、历史、文件/图片、提醒、用量/配置只读。
2. 内核代码保持不动；只新增必要的 API 门面和用量记录。
3. App 的鉴权、设备配对、离线队列先做简单版。
4. 每完成一个功能，自测 + 记录，不自动合并/推送。
5. 等你回来验收后，再进入 Phase 1 的 API 边界和用量面板。

---

## 9. 风险与决策记录

- **不一次性重构**：先模块化，后拆服务；避免个人项目被架构拖垮。
- **凭证不进数据面**：数据面只存状态/元数据。
- **工具代码不远程执行**：共享注册表 + 签名 + 内核沙箱执行。
- **长任务必须有预算/审批/暂停**：否则会失控。
- **单人阶段不引入企业组件**：不上 K8s/消息队列/多租户数据库，先用 JSON/SQLite。
- **代码变更遵守流程**：新分支、自测、提交；合并/推送要用户确认。

## 10. 术语

- **边缘内核**：运行在用户主机上的 Jarvis，负责执行。
- **数据与控制面**：集中管理租户、数据、工具注册表、策略、审计。
- **管理系统**：手机/PC 客户端，负责交互与治理。
- **工具注册表**：工具的元数据/版本/权限，不是工具代码副本。
- **任务卡**：长任务的目标、计划、约束、审批、预算、状态。
- **tenant_id**：租户标识，从第一天预留，先单租户。
