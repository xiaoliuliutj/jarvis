# Jarvis 开发方向（长期基线）

> 确认时间：2026-11-27
> 两个方向并行保留，**都从现有 Jarvis 项目扩展**，不另起炉灶。

---

## 方向一：多 Agent 个人工作处理助手（「AI 公司」架构）

把 Jarvis 从单一助手扩展成一个「一人公司」：

- **Jarvis = HR / 项目经理**：负责招募（创建）角色 agent、分配任务、检查质量、纠正错误
- **角色 agent 各司其职**，例如：
  - 需求澄清 agent：把模糊需求转成具体、可验收的需求卡
  - 方案 agent：把需求卡转成技术方案/任务拆解
  - 开发 agent：按方案实现（分支隔离）
  - 测试/验收 agent：验证结果、产出验收报告
- **可并行**：多个 agent 同时处理不同任务，结果汇总给用户

### 复用现有能力

- 子代理（subagent）能力：框架已支持，一个回合可并行派发多个子代理
- 多会话模型：per-principal 多 session，可承载多个「角色」
- 调度器：不同 principal 可并行（全局并发当前 2，可调）
- 工具 / 记忆 / 工作区 / 定时任务体系

### 待建设

1. **角色注册**：名称、职责 prompt、工具白名单、模型与预算
2. **任务协议 / 看板**：状态机（需求→澄清→方案→开发→测试→验收）+ 结构化任务卡（输入/输出契约/验收标准），禁止纯自然语言交接
3. **多 agent 视图**：App 端查看各 agent 的状态与产出（当前 App 只显示单会话）
4. **并行调度与防冲突**：并发上限、git 分支/worktree 隔离、写锁、预算控制

### 阶段路线（先工作流，后团队）

1. **阶段 1（MVP，无需改框架）**：Jarvis 用现有子代理跑通一条完整流水线（项目经理 + 需求 + 开发 + 验收），用真实任务验证质量与成本
2. **阶段 2**：常用角色做成常驻 agent 定义（配置文件 + 权限隔离 + 独立记忆），任务板管理
3. **阶段 3**：多 agent 看板 UI + 并行调度升级 + 预算/配额

### 原则

- 结构化交接（任务卡），不靠「开会」
- 先 3 个角色，别一上来搭十个部门
- 子代理的汇报要主代理复核（汇报与实际工作之间会丢信息）
- 并行写代码必须分支隔离

## 方向二：企业级 AI 应用服务提供方

把 Jarvis 演进成「企业级 Agent 平台」，对外提供 AI 应用服务：

- 边缘内核（每用户一份）+ 管理面（App/PC）+ 数据与控制面（租户/身份/用量/工具注册表/审计）
- 详见基线文档：`docs/enterprise-agent-platform.md`（2026-11-25）

---

## 两个方向的关系

- **同源**：都以现有 Jarvis 内核、工具系统、App 体系为基础
- **方向一是纵深**：单机能力的组织化（数字公司 / 个人工作助手）
- **方向二是横向**：服务化、多租户化（企业平台）
- **共享基础设施**：任务卡机制、审批通道、审计日志、工具注册表、多会话/多 agent UI —— 建议两方向共用同一套「任务 + 审批 + 多 agent 视图」

## 近期优先级

1. 方向一先跑 MVP 验证（成本低、见效快）
2. 同步把「任务卡」格式定下来，作为两个方向的共同基础
3. 方向二按既有基线稳步推进，不抢跑

## 近期可执行验证

- 挑一个真实任务，跑一次「项目经理 + 需求澄清 + 开发 + 验收」子代理流水线，记录质量、耗时、token 成本
- 根据结果决定是否进入阶段 2

## 方向三：PC 前端统一与数据同步（2026-11-28 追加）

### 背景

- PC 端 React 前端约 1200 行，只有会话、历史、基础设置
- App 端前端 4600+ 行，覆盖会话、工具、用量、模型、价格、审批、文件
- PC 使用 `pc-main`（独立 principal），App/微信使用 `user_1efb13a1ec`，**两套会话/记忆/工作区，数据本来就不同步**

### 目标

1. PC 端获得与 App 相同的功能（工具管理、用量、模型、价格、审批等）
2. PC 与 App 共用同一个账号 / principal 与后端数据，实时同步
3. 主人在 PC 上的日常使用体验优先

### 方案对比

| 方案 | 做法 | 工作量 | 备注 |
|---|---|---|---|
| A. 管理台窗口 | Electron 增加「PC 管理台」窗口，直接加载 Bridge 的 `app/web`（127.0.0.1:17779），用 App 同一账号登录 | 1~2 小时 | 功能和数据立即全量同步；移动优先布局，宽屏居中 |
| B. 响应式共用前端（推荐） | 把 `app/web` 改成 PC/手机共用的响应式前端（宽屏三栏：会话/工具/用量/设置），Electron 主窗口直接加载本地 Bridge | 2~4 天 | 一套前端双端使用；需补文件拖拽、通知等 Electron 原生能力 |
| C. React 逐页重写 | 用 React 重做全部管理页，PC 走 Bridge API | 1~2 周 | 两套 UI 长期维护，不推荐 |

### 数据同步原则

- **同一后端 + 同一 principal 即天然同步**；PC 登录 App 账号即可看到相同会话、记忆、工具和用量
- `pc-main` 后续可退化为「维护会话」，日常聊天统一走 owner 账号
- Bridge 需要常驻；Electron 可检测并自动拉起，避免「PC 能用但 Bridge 没开」

### 实施顺序

1. 先落地方案 A，验证 PC 端全功能体验与数据同步
2. 确认后投入方案 B，PC/手机共用一套响应式前端
3. 迁移完成后评估是否保留 PC 独立 React UI（可退化为维护台）

### 原则

- 不重复造两套 UI；管理类页面（工具/用量/模型/设置）以 Web 前端为主
- 数据同步靠「同一 principal」，不做跨 principal 的数据桥接
- PC 优先不等于重写：先复用，再优化布局
